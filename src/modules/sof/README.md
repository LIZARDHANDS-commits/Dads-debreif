# SOF Dashboard

The weather screen a Supervisor of Flying keeps open on a desk: the weather now and forecast at home and at the alternates, each report with its age. The spec is [`docs/modules/sof/spec.md`](../../../docs/modules/sof/spec.md); the plan is [`docs/modules/sof/plan.md`](../../../docs/modules/sof/plan.md). This folder holds tasks 1 to 5 so far: the wave, card and caution decisions, and a screen with live weather, the caution banner, the waves and the 24-hour timeline. The map and the rest come in later tasks.

## Site profiles

The SOF will run at more than one base, so what is specific to a base lives in one **site profile** per base in `sites/`, and the SOF reads the profile for the current home field (`app.airfields.home().icao`) wherever it used to read a Moose Jaw constant, again whenever home changes. A profile holds: `airspace` (the 3D view's areas, each with its source), `watchedAreas`, `towns`, `anchorStations`, `tourTargets`, `magVarDegE` (`{ value, source }`), the map box, whether the VNC `charts` are available, the `routes` it draws (`training` is the Debrief's routes layer, `tacnav` the TACNAV lines in 3D), the `sources` it uses (`radar`, `lightning`, `satellite`, `warnings`, `modelClouds`, `modelCloudMask`, `notams`, `alerts`, `fronts`, each naming its service and credit), the `credits` words, and `standards` (the weather limits, or `null`). Moose Jaw's profile (`cymj.js`) only points at the modules that already held the data, so there is one copy of each number; it is used for CYMJ and for any other Canadian field (ICAO starting with C), which is what the SOF did before profiles. Any other field gets `GENERIC` (`generic.js`): everything empty, every source `null`, `standards: null`.

A source that is `null` is never treated as "nothing found". Its feed is not started, and its line reads "Lightning: no source for this base, can't tell" (amber, with a warning symbol, never a tick) in the map strip, the 3D strip, the model panel and the cards (NOTAMs, SIGMETs and PIREPs). The near-home lightning check (`lightning.js`, `hasSource`) can never say "No lightning within 20 NM ✓" for such a base. Part A changes nothing on screen for Moose Jaw.

**Part B (V2.188): the US bases and "Limits not set".** The seven US T-6 bases (Laughlin KDLF, Vance KEND, Randolph KRND, Columbus KCBM, Sheppard KSPS, Whiting Field KNSE, NAS Corpus Christi KNGP) each have a profile with `usualAlternates` (Dad's for Laughlin; agreed guesses for the rest), towns from GeoNames, a tour of the circuit and one nearby field, NOAA WMM2025 magnetic variation, the WPC fronts (which cover the US) and nothing else yet: no airspace, every other source `null`, `standards: null`. Moose Jaw's profile has `usualAlternates` too (the airfields' defaults, by reference). **SOF settings → Home base** picks a base: it sets home and that base's usual alternates in the shared airfields setting, so Settings → Airfields and the SOF always agree, and it follows a home set in Airfields ("Other (set in Airfields)" for a field with no profile). The choice needs the app's shell to hand modules the airfields setting's `update()` (`src/shell/host.js` passes it read-only today); until it does, the section names the home base and says it is set in Settings, under Airfields.

When the home base's profile has `standards: null` (a US base, or any field on the generic profile), nothing reads as checked against a limit: the home card, its row and the 3D pin say grey "Limits not set for KDLF"; each alternate amber "⚠ Incomplete" (SOF-32); the wave chips "Limits not set for KDLF" and "N alternates incomplete" (never "No alternate needed" or "meet"); the timeline and the strip show "Limits not set for KDLF" and hatch nothing; the banner raises no limit caution (no below-limit METAR or TAF, no crosswind red). The key line, on hover and in the timeline key, reads "No weather limits have been given for this base yet; the weather shown is not checked against any." The METAR, TAF, flight category and NATO colour state still show, and dangerous weather (thunderstorms, CB, freezing precipitation) still raises its caution. Moose Jaw and every Canadian home are unchanged.

## What the screen shows

- **SOF bar:** the DTG, the weather feed in words and a symbol (`Weather 2 min ago ✓`, `Refreshing…`, `STALE 48 min ⚠`, `Failed, showing 12 min old ⚠`, `Off`), and Refresh. Traffic is a map layer (SOF-7, task 7b), not a link here. The feed status can be focused and says where the weather came from and when it asks again.
- **Airfield cards:** home, then each alternate. Each shows the raw METAR and TAF as text with the report's own time and age, `STALE` in words for an old report (greyed), the words for a missing, cancelled or NIL report, `Last refresh failed` for a report the last round couldn't refresh, and the limit result in words.
- **Every feed failing:** its own row above the cards says so, names which sources failed and when, and says how old the reports still shown are. The cards keep the last reports.
- **Settings:** one closed menu, "SOF settings", holds the alternate trigger (Local (MTCA) 2000/3 by default, or Cross-country 3000/3) and the two limit numbers. A typed limit snaps up to the next 100 ft or quarter mile when committed, so the box shows what the check uses. The banner switch and the lightning radius have defaults (`SETTINGS_DEFAULTS`) but get their controls in tasks 3 and 7. Reset puts every setting back. Stored settings are range-checked on read.

- **Caution banner:** one line per caution with its level in words and a symbol; Acknowledge and Acknowledge all. Marked words inside the report are not built yet (wx exposes no word positions). "Show the new-caution banner" in SOF settings turns it off (on by default); cautions are still worked out and acknowledgements pruned. The lightning hook is `screen.extraCautions`.
- **Waves:** up to 5, home local time with the zone, Today or Tomorrow. Each has a chip; pressing it lists every hit and shows that wave's result on each alternate card. New waves start with blank times.
- **24-hour timeline:** a row per airfield, Zulu axis first (Local first follows the app setting) with a local row, NATO-state pieces labelled in words, hatched when below limits, wave bands with landing and +1 h marks, the METAR mark and the now line. Hover or focus shows the card in words. Open by default; the choice is kept under `timelineCollapsed`.
- **3D view (SOF-39, phase 1):** the **3D** button in the map controls swaps the map area for a 3D picture of the 450 NM square round home (it was 250; Dad, 7 Oct) (it reads **2D** while shown, and the ADS-B Exchange view and 3D never show together). Satellite ground, radar and lightning on it with the same stale fading, home and alternates as pins with their category in words, each METAR's cloud layers as flat decks 10 NM across, the 25 and 50 NM rings, and "Heights ×5" in the corner. Drag to turn, wheel or pinch to zoom, Home (or the Home key) resets. A pin is a button that shows its card's result line, and the camera never moves on a click. An airfield outside the square is named, not drawn. No WebGL: the button stays and says why on hover. Nothing in it raises or clears a caution.
- **Live aircraft in 3D (SOF-39 phase 4, SOF-40):** with the traffic relay's address set, the same **Traffic** switch that drives the 2D layer also shows the relay's aircraft in 3D (one feed, the 2D layer's own checks, the same stale fade and the same pause for a hidden tab). Each stands at its position and pressure altitude (times the height scale; "ground" is the field's elevation) pointing along its track (degrees true; the 3D world is north up). A T-6 (type `TEX2`) is the CT-156 model drawn large, with a cyan halo, a drop line to the ground and its tag always on ("TEX21 5,500": callsign or registration or hex, then hundreds of feet, or FL from 18,000 ft). Other aircraft are small grey stand-ins whose tag shows on hover, on `]` and `[` (step through them, as in 2D) or all the time when the Labels choice is on; military ones are amber with a ring. Clicking an aircraft or its tag shows the 2D hover facts in a small tag, and never moves the camera. An aircraft with no height is not drawn (the line says how many), and over 150 only the nearest are drawn (T-6s first). If the relay fails the aircraft fade and go as in 2D, and the line says "Traffic unavailable, last good 1842Z". The credit "Aircraft: adsb.lol (ODbL 1.0)" shows while the layer is on.
- **Airspace and the TACNAV routes in 3D (SOF-39, phase 3):** two toggles under the model controls, **Airspace** and **TACNAV** (both on, `aria-pressed`), and a closed "Airspace key". Each airspace entry in `src/airfields/airspace/data.js` is a see-through prism from its floor to its ceiling (about 8 % fill, `AIRSPACE_FILL_OPACITY`, an estimate; drawn without depth writing so clouds and aircraft read through it) with a thin outline on its top and bottom rings and its corners. Edge colour by kind, also said in words in the key: restricted or danger areas red (danger is red only), advisory areas amber, terminal airspace blue, control zones light blue, MTCA cyan, other grey. Each has a label at the middle of its top, "CYR303 SFC–FL180": a restricted area's label always shows its limits, the others show the id and open to the limits on hover or focus (they are buttons), and the hover text gives the kind, class and source. SFC is the ground at home's elevation; AGL is home's elevation plus the height (ground taken as flat prairie, an estimate); FL is read as feet above sea level (pressure altitude taken as altitude, an approximation); UNL is drawn up to 60,000 ft; all times the height scale. The routes of the Debrief's `ROUTES` with TAC in the name (TAC NAV 2, TAC NAV 3, TACNAV 1, TACNAV 4, TAC test North and South) are dashed lines at home's elevation plus 500 ft, named at their first point, with the note "500 ft AGL, ground taken as flat at CYMJ's elevation (estimate)" in the key. While `AIRSPACE` is empty the Airspace toggle reads "Airspace (no data yet)" and is disabled with the reason on hover. An entry that fails `checkAirspace` is skipped and named in the key, never drawn wrong. Nothing in it raises or clears a caution, and it is not a chart or for navigation.

## Changing something

- **The 3D height scale:** "3D height scale" in SOF settings (`heightScale3d`, 5 by default, 1 to 20; an estimate for readability, SOF-39). The view's corner says the number in use.
- **How solid a cloud deck is:** `COVER_OPACITY` in `scene3d-model.js` (FEW 25 %, SCT 45 %, BKN 70 %, OVC 90 %; estimates, SOF-39). The deck width is `DECK_NM` (10) and the square is `AREA_NM` (450 by default; the "3D area" setting: 450, 600 or 900).
- **How the airspace looks, and how to add an entry:** `AIRSPACE_FILL_OPACITY` (0.08), `TACNAV_AGL_FT` (500), `VIEW_TOP_FT` (60,000) and `CIRCLE_SIDES` (64) in `src/airfields/airspace/model.js`; the edge colours (`KIND_COLOURS`) and the route dashes in `src/ui-kit/airspace3d.js` (estimates for readability, SOF-39). To add an airspace, write one entry in the shape at the top of `src/airfields/airspace/data.js`, with its `source`; the view checks it and says in its key if it skips it.
- **How the 3D aircraft look:** `SIZE_PX` (a T-6 44 px long on the screen, others 22, a helicopter 24, an airliner 25, a business jet 21, a light aircraft 19, a military transport 27, a fighter 21, a dot 9) and `COLOURS` in `traffic3d.js` (estimates for readability, SOF-39); `ICON_SCALE` (0.7, 1, 1.4), `MAX_3D_AIRCRAFT` (300) and `T6_TYPE` (`TEX2`) in `scene3d-model.js`; each kind's shape in `aircraft3d.js` and its 2D glyph in `map-draw.js` `GLYPHS`; the kind lists in `aircraft-kind.js`; the aircraft's lighting is in `build()` in `view3d.js`.
- **The model layers' numbers** (`model-clouds.js`): the grid (`GRID_SIZE` 13, so 37.5 NM apart), the two requests (`HRDPS_PROFILE`, 13 levels from ECCC's 2.5 km model (925 hPa added 7 Oct), and `GEM_PROFILE`, the global model's 8 levels: HRDPS is asked first and is slow, about 40 s, so the global answer shows first and HRDPS replaces it; the levels HRDPS answered on 7 Oct 2026 are in `HRDPS_TRIED_HPA`), the variables and levels (`HOURLY_VARIABLES`, `CLOUD_LEVELS_HPA`, `WIND_LEVELS_HPA`), the cloud line (`CLOUD_COVER_THRESHOLD_PCT`, 30 %; estimate, SOF-39), the low, mid and high stages (`CLOUD_STAGES_FT_AGL`: 6,500 and 20,000 ft above the ground), how long an answer is kept (`STALE_MS`, 3 hours), how often it is asked for (`REFRESH_MS`, 1 hour) and the retry after failures in a row (`RETRY_STEPS_MS`: 10, 20, then 40 minutes, to stay inside Open-Meteo's free daily limit; an estimate). The slabs' look is in `cloud-field.js` (`SLAB_SHEETS` 2 since V2.198, `MIN_SLAB_FT`, the noise; estimates, SOF-39). The cloud sheets' look is also in `model-clouds.js`: `CLOUD_SHEET_PX` (256), `CLOUD_SHEET_ALPHA_MAX` (0.85), `CLOUD_SHEET_BLUR_PX`, `CLOUD_SHEET_COLOURS` and the curve `sheetAlpha` (estimates, SOF-39). How the barbs and the freezing sheet look is in `model-layers3d.js`.
- **How the 3D terrain and towns look:** the height scale is the same "3D height scale" setting; `SHADE_GAIN`, `TERRAIN_ZOOM` and `MAX_TERRAIN_TILES` in `terrain-model.js`; `TERRAIN_APPLY_MS` and `TERRAIN_DEPS_MS` in `view3d.js` (how often the ground is re-read as tiles arrive); the towns' `CELLS_PER_RADIUS`, `MAX_TOWN_BLOCKS` and heights in `towns3d.js` and their places and sizes in `towns-data.js` (estimates). - **The weather layers in 3D:** the estimates are named in `weather3d-model.js` (`RADAR_DEFAULT_AGL_FT` 8,000, `LIGHTNING_DEFAULT_AGL_FT` 25,000, `SATELLITE_DEFAULT_FT` 30,000, `FRONT_WALL_FT` 6,000, `FLOW_FT_PER_S_PER_KT` 600, `FLOW_PARTICLES` 300) and every one is said in the view's "Weather key".
- **The approaches:** run `node tools/cifp-approaches.mjs --cifp /path/outside/the/repo/FAACIFP18` each 28-day CIFP cycle (the raw file never goes in the repo) and commit `sites/approaches/`. The corridor's widths and heights are `CORRIDOR`, the estimate's 10 NM, 3° and 50 ft are `ESTIMATE`, the holds' look `HOLD_DRAW` and the colours `APPROACH_GROUPS`, all in `approaches-model.js` (estimates); the line looks are in `approaches3d.js` and `map-draw.js` (`APPROACH_2D`).
- **The tour:** `TOUR_TARGETS` (add a target here: a `field` by ICAO or an `aircraft` kind), `TOUR_DWELL_S` (20), `TOUR_FLY_S` (2) and `TOUR_PITCH_DEG` in `tour-model.js`.
- **How often the weather is asked for:** `REFRESH_MS` in `weather.js` (5 minutes, D67). `wake()` refreshes at once when the tab comes back and a round is due.
- **When the weather feed reads STALE:** `STALE_FEED_MIN` in `screen-model.js` (15 minutes, three missed rounds). A single report's own staleness (75 minutes for a METAR, a TAF past its end) is wx's, through `cards.js`.
- **How long a kept report is still shown:** `MAX_KEEP_MS` in `reports-store.js` (3 days). It shows with its age and STALE.
- **A limit's step:** `RANGES` in `settings-model.js`; limits always snap up, never down.
- **A default setting:** `SETTINGS_DEFAULTS` in `settings-model.js`. The trigger presets themselves are wx's (`HOME_TRIGGERS`).
- **The credits line:** `CREDITS` in `screen-model.js`. Add each new source here as its layer lands.
- **The card's layout:** `children()` in `cards-view.js`, and the classes in `sof.css`.

## Things to know

- **What's kept in the browser** (through `app.storage`, scope `sof`): the settings, the last good reports, the wave plan (`plan`), the acknowledged cautions (`cautionAcks`) and whether the timeline is closed (`timelineCollapsed`). If the browser blocks storage they last for the visit only.
- **The 3D view asks for its own pictures** (`feeds3d` in `map.js`): radar, lightning and the GOES cloud picture over the whole 450 NM square, only while 3D is shown (the 2D map's pictures cover only what the 2D view last asked for). They lay on the 3D ground (each only when its 2D layer is on) and, read on a grid, make the radar shafts, the lightning bolts and the satellite sheet. The backup radar (RainViewer tiles) is not drawn in 3D.
- **The model feed** (`createModelFeed` in `model-clouds.js`, started by `map.js` when 3D opens and stopped when it closes) asks through `map-fetch.js` (30 s for the global model, 180 s for HRDPS, 3 and 4 MB caps, no cookies, no redirects) and keeps the last good answer in memory only. Its reply is checked field by field in one function (`checkModelReply`: 169 points, the same times and array lengths for every variable, every number finite and in range); one wrong value fails the whole reply. A `null` is no data for that one value (cloud cover null is not cloudy, a null height drops that level, a null wind draws no barb, a null freezing level is left out of the mean), but nulls in more than half of all the values fail the reply too ("Model data incomplete"). Wind direction is shown in °M with 9° East variation (Patrick, TR-65); `MAG_VARIATION_DEG_E` in `model-clouds.js` repeats Traffic's number because modules do not import each other and there is no shared copy yet.
- **Timers** come only from the module's scheduler scope: the refresh's 5-minute timer (via wx's `startRefresh`) and one 15-second tick that redraws ages and the DTG. Requests are made with an abort signal that unmount fires.
- **Chrome logs a 404 as a console error.** Datamask answers 404 for a station it doesn't have, and that is logged by the browser, not by this code. It only happens when MET Norway has no report for a station, which is also when the card says `No METAR from MET Norway or Datamask`.
